# AGENTS.md — rules for AI coding agents

These rules apply to **every prompt** in this repository, for any agent
(Claude Code, Codex, others). They are mandatory, not suggestions.

- **This file** says *what you must always do*.
- [CONTEXT.md](CONTEXT.md) says *how the project works*: architecture, file
  map, invariants, recipes and pitfalls. Read it before your first change in
  a session.

If a rule here conflicts with a request from the user, follow the user and
say which rule you departed from. If the user changes a rule durably, update
this file in the same task.

---

## 1. Documentation is part of every change

After **any** change to the project (code, configuration, workflows, scripts,
dependencies, data layout), update the documentation **in the same task**,
before you report the work as done.

| File | Audience | Update it when the change affects… |
|---|---|---|
| [README.md](README.md) | Developers | setup, commands, architecture, configuration, data layers or storage, extension guides, CI/CD, troubleshooting |
| [CONTEXT.md](CONTEXT.md) | AI agents | file map, invariants, recipes, commands, pitfalls met, roadmap context |
| [PROJECT.md](PROJECT.md) | Site users | what users see or can do, how numbers are computed, data sources, schedule, features (now and next), limits |
| AGENTS.md | AI agents | the rules themselves |

- Check all three documents each time. Most changes touch README and
  CONTEXT; PROJECT changes whenever user-visible behaviour, data sources or
  the roadmap change.
- Keep the documents true: remove or rewrite statements your change made
  wrong. Never leave a known inaccuracy.
- Write each document for its audience. PROJECT.md uses no code names; README
  and CONTEXT name files and commands.
- When you hit a new pitfall (a non-obvious failure and its fix), add it to
  CONTEXT.md §8.
- In your final reply, list which documents you updated, or say explicitly
  why none needed a change.

## 2. Languages

- **English** for code, comments, docstrings, documentation files, commit
  messages, pull request texts and log messages.
- **French** for replies to the user in the conversation.
- User-facing site text exists in **French and English**: UI strings in
  `web/src/lib/i18n/fr.json` and `en.json` (same keys), content labels as
  `{fr, en}` objects in `config/`. Never add a string in only one language.

## 3. Git and GitHub

- Work on `dev` (or a branch merged into `dev`). Never push to `main` or
  `gh-pages`, never force-push, never open a pull request against `gh-pages`.
- `main` changes only through a pull request from `dev` with CI green.
- Commit, push, open pull requests, change GitHub settings or run
  `scripts/setup-github.sh` **only when the user asks**.
- Never commit `/data`, virtualenvs, `node_modules`, `web/dist`, secrets or
  tokens.

## 4. Architecture rules

- **Medallion layers.** Code goes in the layer it belongs to:
  `bronze/` (`Extractor*`, raw data only), `silver/` (`Transformer*`, clean and
  typed), `gold/` (`Aggregator*`, KPIs), `diamond/` (`Displayer*`, site JSON).
  File `{prefix}_{name}.py` holds class `{Prefix}{Name}`, registered with its
  decorator.
- **Configuration first.** Massifs, stations, KPIs, labels, tiles, layout and
  sources live in `config/`. Never hard-code them in Python or Svelte.
- **Three kinds of data.** Hand-written facts in `config/*.yaml`; slow-changing
  fetched facts as reference data in `config/reference/` (refreshed with
  `bluebird reference`, never by the daily run); weather as daily data.
- **One contract.** After changing `config.py` models or `diamond/models.py`,
  run `uv run bluebird schemas` and `npm run gen:types`, and bump
  `schema_version` for breaking diamond changes.
- **Generated files** (`config/schemas/`, `web/src/lib/generated/`,
  `config/reference/`, `web/public/data/diamond/`) are regenerated by their
  command, never edited by hand.
- **Hosting and storage stay on GitHub.** Adding an external service, API key
  or paid dependency needs the user's approval first.
- **Respect data sources.** Keep requests within rate limits, declare every
  source's `attribution` in `config/sources.yaml`, and never fetch live data
  under a past date.

## 5. Quality bar

- Add or update tests with every behaviour change (pytest for the pipeline,
  Vitest for the site).
- A task is done only when the checks of CONTEXT.md §9 pass:
  ruff format and lint, `bluebird validate`, `bluebird schemas --check`,
  pytest, `npm run gen:types` with no diff, `npm run check` with
  0 errors and 0 warnings, `npm test`, `npm run build`, and actionlint for
  workflow changes.
- UI changes are checked on a 390 px wide viewport, in light and dark mode,
  in French and English.
- Report failures honestly: if a check fails or was skipped, say so.

## 6. End-of-task checklist

Before your final reply, confirm each line:

- [ ] README.md, CONTEXT.md and PROJECT.md reviewed and updated where needed.
- [ ] New pitfalls added to CONTEXT.md §8.
- [ ] Tests added or updated; all checks of CONTEXT.md §9 pass.
- [ ] Generated files regenerated, not hand-edited.
- [ ] No string added in only one language.
- [ ] Nothing committed or pushed unless the user asked.
- [ ] Final reply, in French, says what changed, which documents were
      updated, and what is left to do.
